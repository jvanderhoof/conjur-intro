# conjur-env

Translate a customer's description into an `environments/*.yml` spec, show one gate, and
hand off to `bin/env`. This skill adds no provisioning logic of its own. Ordering,
preflight and verification belong to `bin/env`, and what a spec may contain belongs to
`environments/schema.json`.

The repo is the conjur-intro checkout in the **current working directory**. Open every
repo path below (`environments/schema.json`, `bin/env`, `docs/`) exactly as written,
as a relative path. Never build an absolute path from this skill's own location: the
skill may be loaded from a different checkout than the one you are working in. Only
`reference/` lives next to this file.

## 1. Read the description

The input is either pasted prose or a path to a local file. If it is a path, read the
file. Do not fetch anything from a ticket system.

## 2. Map it to the spec

Read these two files:

- `environments/schema.json`: the fields that exist, what each one accepts, and how
  they constrain each other. It is the only source for constraints. Do not work them
  out from memory or from this file.
- [reference/vocabulary.md](reference/vocabulary.md): what customers call each field,
  and what customers commonly describe that no field can express.

Go through **every property in the schema**, including the ones nested under `leader`.
Sort each one into one of three kinds:

- **Stated.** The description says it, in whatever words. Record the value, and the
  phrase you took it from.
- **Unstated.** The description does not settle it. A schema `default` does not settle
  it.
- **Gap.** The customer describes something the schema has no field for. The
  vocabulary file's gap list covers the common ones.

`events` is never a question. Write it with the value the schema accepts for "no
transitions". Any transition the customer describes is a gap.

## 3. Ask about everything unstated

Ask about every unstated field before writing anything. Put all the questions in one
batch, and say which phrase in the description each question comes from. Never fill a
field in from the schema's default, from a "typical" production shape, or from a
guess. A repro is worth the extra turn.

If a stated value is ambiguous, ask too. "Three replicas" could mean standbys or
followers, and the vocabulary file says how to tell them apart.

Keep going until every field is stated or answered. If nobody can answer, stop and
say what is still unknown. Do not write a spec with holes in it.

## 4. Write the spec

Write it to `environments/<short-name>.yml`. The repo gitignores specs at that path,
and customer details must never land in a tracked file. Confirm the path is ignored with
`git check-ignore <path>`. Never write into `environments/examples/`.

- Write **every** schema field explicitly, including `events` and those left at a
  default. A spec this skill writes must not depend on the schema's defaults, so that
  it behaves the same whatever the defaults later become.
- Quote the version.
- Use only keys the schema defines. If something has no field, it is a gap. Never
  invent a key and never repurpose one. An invented key fails validation, and that
  failure is correct.
- If the customer has more of something than the schema accepts, write the largest
  value the schema accepts, and list the rest as a gap that says how many were asked
  for and how many will be built.
- Put a comment at the top saying which ticket or description the spec came from, and
  that it was generated by this skill. Do not copy customer names, hostnames or
  passwords into it.

Then validate it. Nothing else happens until it validates:

```sh
bin/env --plan environments/<short-name>.yml
```

A rejection names the offending field. Fix the translation, not the schema. Never edit
`environments/schema.json`, `bin/env` or any other tracked file to make a spec pass.

If you cannot run it at all (no shell, no docker), still show the gate. Say plainly
that the spec is unvalidated, and do not provision it.

## 5. The gate

Check whether an environment already exists in this working copy:

```sh
docker compose ps --all --format '{{.Name}} ({{.State}})'
```

If one does, run `bin/env --plan --recreate environments/<short-name>.yml`. Its output
states what recreating destroys.

Then present **one** message with all of the following, and ask a single question:
provision this?

1. **The spec.** The file's contents, with the phrase or answer each value came from.
2. **Set up by hand.** Every gap, one line each: what the customer described, and why
   the spec cannot express it. Write "none" if there are none.
3. **The plan.** The `bin/env --plan` output, verbatim.
4. **What will be destroyed.** Only if an environment exists: the running containers,
   and the `--recreate` destruction notice, verbatim.

Proceed only on a clear yes. Anything else, including silence, a question, or "looks
roughly right", is not a yes. Change what they ask for and show the gate again. Never
ask a second confirmation after a yes, because `--recreate` has no prompt of its own
on purpose.

## 6. Provision and report

Record `git status --porcelain` first. Then run the build in the background, because it
takes several minutes:

```sh
bin/env [--recreate] environments/<short-name>.yml
```

Pass `--recreate` only when an environment existed and the gate said so. When the
build finishes, report:

- The verification table, verbatim, and whether `bin/env` exited zero.
- On failure, the failing step or rows, and the matching part of
  `docs/environments.md#troubleshooting`. Do not retry, and do not work around it.
- Any tracked file that `git status --porcelain` now shows as changed. Report it
  without reverting it. `bin/dap --enable-auto-failover` rewrites `policy/cluster.yml`,
  which is known debt.
- The gaps again, as the list of what still has to be set up by hand.

If the engineer then asks you to set up a gap, never edit a tracked file to do it. Use
raw commands against the running containers (for example `docker compose exec <node>
evoke ...`), or an untracked compose overlay passed with `-f`.
